Assignment 04 – CI/CD Pipeline Integration
Total Marks: 100   |   Weeks Covered: 10 – 14   |   CLO: CLO2

OBJECTIVES
Students will design and implement a complete CI/CD pipeline for a containerized web application by integrating a CI workflow (triggered on a Pull Request) with a CD workflow (triggered on a merge/push to the develop branch). The assignment covers creating a fresh GitHub repository, versioning the assignment document, configuring GitHub Environments, managing secrets, and chaining two GitHub Actions workflows.

By the end of this assignment, students will be able to:
Create a new GitHub repository from scratch and establish a proper branching strategy.
Version the assignment question paper inside the GitHub repository.
Create and configure a GitHub Development Environment with appropriate secrets.
Design and implement a CI workflow triggered by a Pull Request targeting the “develop” branch.
Design and implement a CD workflow triggered by a push event on the “develop” branch.
Verify end-to-end automated delivery from a code push to a live deployment on Render.

SCENARIO
Your team is the development crew for TaskFlow, a lightweight task-management web application consisting of five HTML pages. The Team Lead sets up the repository, Dockerfile, shared stylesheet, and the CI/CD pipelines. Each team member is then individually responsible for building one specific page of the application, following the full Git, GitHub, and Docker flow independently.

The 5 pages of the TaskFlow application and their assignment are defined in Table 3 below. The Team Lead takes Page 1 (Home / Dashboard) in addition to their setup responsibilities.

Table 3: TaskFlow Page Assignment
Sr #
Page File
Page Name
Page Responsibility
1
index.html
Home / Dashboard
Overview of all tasks: summary counts (total, pending, completed), a welcome message, and navigation links to all other pages.
2
add-task.html
Add Task
An HTML form allowing the user to enter a new task , fields for task title, description, due date, and priority (High / Medium / Low).
3

Task List
A table listing all tasks with columns for title, due date, priority, and status. Includes basic filter buttons (All / Pending / Completed).

A page displaying the full details of a single selected task, with an option to mark it as complete or delete it.
5
about.html
About / Help
A page describing the TaskFlow application, its purpose, and a simple usage guide explaining how to navigate and use the app.

Each member's individual workflow:
Create a personal feature branch from “develop” using the naming convention: feature/<member-github-username>/<page-name>  (e.g., feature/ali-hassan/add-task).
Build the assigned HTML page with appropriate content and link it to the shared style.css.
Commit the page file and push the feature branch to GitHub.
Open a Pull Request (PR) targeting the “develop” branch. This triggers the CI workflow automatically.
Once CI passes and the PR is reviewed and approved, the Team Lead merges the PR. The merge generates a push event on “develop”, which triggers the CD workflow and deploys the updated application to Render.

Complete automated flow:  Feature Branch → PR opened → CI builds & pushes Docker image → PR merged → push on “develop” → CD deploys to Render → Live TaskFlow updated with the new page.

CI PIPELINE REQUIREMENTS  (.github/workflows/ci.yml)
Trigger: The CI workflow must be triggered by a pull_request event targeting the “develop” branch only.

The CI workflow must include the following steps in order:
Step 1 – Checkout: Check out the repository code using actions/checkout.
Step 2 – Docker Login: Authenticate with Docker Hub using the DOCKERHUB_USERNAME and DOCKERHUB_TOKEN repository secrets.
Step 3 – Build Image: Build the Docker image from the Dockerfile in the project root.
Step 4 – Tag Image: Tag the image using a meaningful strategy , at minimum the 'latest' tag; optionally also tag with the short commit SHA (github.sha).
Step 5 – Push Image: Push the tagged image to Docker Hub.

Additional requirements:
The workflow must fail the entire run if any step fails, preventing a broken image from being available for deployment.
The CI status check must appear as a required check in the Branch Protection Rules on “develop”.

CD PIPELINE REQUIREMENTS  (.github/workflows/cd.yml)
Trigger: The CD workflow must be triggered by a push event on the “develop” branch. This push event occurs automatically when a Pull Request is merged into “develop”.

The CD workflow must include the following steps in order:
Step 1 – Checkout: Check out the repository code using actions/checkout.
Step 2 – Declare Environment: The job must specify environment: development so that the RENDER_DEPLOY_HOOK_URL environment-level secret is made available to the job.
Step 3 – Deploy: Send an HTTP POST request to the Render deploy hook URL using curl:
curl -X POST ${{ secrets.RENDER_DEPLOY_HOOK_URL }}
Step 4 – Confirm: Output a timestamped deployment confirmation message as the final step.

Additional requirements:
The CD workflow file must declare runs-on: ubuntu-latest.
The job must NOT contain any Docker build or push steps , that responsibility belongs exclusively to the CI workflow.
